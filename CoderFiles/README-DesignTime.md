# Design-time support

Generated by the DesignTimeSetup template. This file is overwritten on every run.

See also `README-DependencyInjection.md` — this mechanism sits on top of `ServiceLocator`,
which DISetup generates.

---

## The problem

The XAML designer renders your views in **its own process**. It loads your compiled
assembly to do so, but it never runs `App.xaml.cs` — there is no application startup, so
no `ServiceCollection` is built and `ServiceLocator.Initialize` is never called.

Anything resolving through the locator therefore throws while the designer is rendering:

```
The service provider has not been built. Call ServiceLocator.Initialize(provider) ...
```

The symptom is rarely that message. A binding evaluated during rendering swallows the
exception, so what you see is a **blank canvas** — the window chrome draws, the content
does not — or a designer error with no obvious connection to DI. That is the failure this
mechanism prevents.

It matters because a view whose `DataContext` comes from a static `Instance` property
cannot render without resolving something:

```xml
<Window DataContext="{x:Static viewModels:MainViewModel.Instance}">
```

`x:Static` is not a passive reference — the designer evaluates the property, which resolves
through the locator, which throws.

## The mechanism

Three generated files.

### `DesignTimeDetector` — the flag

In **XpEng.Coder80.Infrastructure**, a static `bool`. Nothing more: it holds whether the current process is
the designer's, and has no dependency on WPF.

### `DesignTimeModuleInitializer` — sets the flag

In **XpEng.Coder03.Views**, the WPF project. It calls
`DesignerProperties.GetIsInDesignMode(new DependencyObject())` — the reliable check — and
writes the result to the flag.

**Why the split.** `DesignerProperties` lives in `PresentationFramework`, which only a
project with `<UseWPF>true</UseWPF>` has. Putting the detection in XpEng.Coder80.Infrastructure would force
a WPF dependency onto a project that has no other reason for one, and would make it
unusable from a console host or a non-WPF front end. So the detection lives where the
reference already exists, and only a plain `bool` crosses the boundary.

**Why a module initializer.** `[ModuleInitializer]` runs when the assembly loads, into any
process — including the designer's, which loads the assembly to render but never runs
application startup. A call from `App.xaml.cs` would never execute in the one case that
needs it.

### `DesignTimeSingleton<T>` — resolve, or fall back

In **XpEng.Coder80.Infrastructure**. Resolves `T` from the container, and falls back to a directly
constructed instance **only** when the container is unavailable *and* the process is the
designer's:

```csharp
public static T Resolve(Func<T> constructFallback) {
    try {
        return ServiceLocator.CurrentProvider.GetRequiredService<T>();
    }
    catch {
        if (!DesignTimeDetector.IsInDesignMode) throw;
        lock (_lock) { return _designTimeFallback ??= constructFallback(); }
    }
}
```

The design-mode condition is the important part. A resolution failure in production or in a
test is a real bug and must propagate. Only the designer — where the container genuinely
was never built — gets a substitute, so a view can still render.

It is a generic static class, so each closed type gets its own fallback field with no
per-type code.

## Wiring a singleton

The template installs the mechanism. It does **not** rewrite your existing classes — that
would mean editing hand-written code, which no template here does. Each singleton needs
its `Instance` property changed by hand, once:

```csharp
// Before — a plain Lazy<T>. Never involves the container, so DI cannot own the lifetime
// and a test cannot substitute it.
private static readonly Lazy<MainModel> _instance = new(() => new MainModel());
public static MainModel Instance => _instance.Value;

// After
public static MainModel Instance => DesignTimeSingleton<MainModel>.Resolve(() => new MainModel());
```

Plus `using XpEng.Coder80.Infrastructure.Services;`.

Two things have to line up, or it fails at runtime rather than compile time:

**The type must be registered.** `[Register]` if its constructor is public; a factory in
`ServiceCollectionExtensions.Manual.cs` if it is `internal` or `protected internal`.
Without a registration, `GetRequiredService` throws — and in production the fallback
deliberately does not fire, so it propagates.

**The fallback lambda must reach the constructor.** `() => new MainModel()` is written
inside the class, so a non-public constructor is fine there.

### Which classes need this

Anything with a static `Instance` that a XAML binding touches — typically the root model
and the root view model. A child view model constructed directly by its parent does not,
since nothing resolves it.

## Recognising the failure

| What you see | Likely cause |
|---|---|
| Blank designer canvas, no error | An `Instance` property still resolves without the fallback |
| Renders in the designer, throws at runtime | The type was never registered; only the fallback was working |
| Blank canvas after adding a new view model | Its `Instance` was not wired to `DesignTimeSingleton` |

A useful check: if a view renders under `dotnet run` but not in the designer, the cause is
almost always a resolution happening before `Initialize` — which in the designer means
always.

### A related trap

A constructor that resolves through the locator makes its type unconstructible in the
designer even when the type itself is wired correctly, because the failure happens one
level down. If a view model's constructor calls `SomeModel.Instance`, guard it:

```csharp
public DashboardViewModel() {
    if (DesignTimeDetector.IsInDesignMode) return;   // skip work the designer cannot do
    // ...load data, resolve services...
}
```

Guard the narrowest thing that actually fails, not the whole constructor — a constructor
that returns early may leave the object in a state the view cannot render either.

## Prerequisite

DISetup must have run first — `DesignTimeSingleton` resolves through `ServiceLocator`,
which DISetup generates. This template checks for it and stops with a clear message rather
than emitting code that will not compile.
