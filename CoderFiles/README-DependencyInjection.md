## Why not just register everything in `Program.cs`?

The common pattern puts every registration in the entry point:

```csharp
builder.Services.AddSingleton<IOrderService, OrderService>();
builder.Services.AddScoped<IUserRepository, UserRepository>();
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();
// ...forty more lines...
```

It works, and for a single-project application it is the right amount of machinery. Past
that it has four specific problems this setup is meant to solve.

**Registration drifts from the type.** A new service means editing a file in another
project. A deleted service leaves its registration behind — one that still compiles, still
runs, and fails only when something resolves it. Here the registration is an attribute on
the class:

```csharp
[Register(typeof(IOrderService))]
public class OrderService : IOrderService { }

[Register(typeof(IUserRepository), ServiceLifetime.Scoped)]
public class UserRepository : IUserRepository { }

[Register(typeof(IEmailSender), ServiceLifetime.Transient)]
public class SmtpEmailSender : IEmailSender { }
```

Delete `SmtpEmailSender` and its registration goes with it. There is no other file to
update and no line left behind naming a type that no longer exists.

**The entry point knows everything.** `Program.cs` ends up referencing every project and
naming every implementation, which is the opposite of what the project structure was for. A
UI project acquires a reference to a data project purely so it can name `SqlUserRepository`
— and once that reference exists the compiler will never again tell you a layer boundary
was crossed, because you opened it yourself to register something.

Here each project registers what it owns and calls the ones it already depends on. No new
references, so the dependency graph keeps describing the architecture rather than the
wiring. If a registration needs a reference that does not exist, that is a design signal
worth having.

**Conflicts are silent.** Register the same service type twice with different
implementations and the container keeps whichever ran last. No error — just the wrong
implementation in production, discovered as behaviour rather than as a stack trace. Here
the scan throws at startup and names every conflict at once. Replacing a registration is
still possible, but it has to be said out loud (`IOverrideRegistrations`), which is the
difference between a decision and an accident.

**Tests get a different container than production.** When composition lives in the entry
point a test cannot call it. The usual workarounds are hand-building a `ServiceCollection`
with the four services that test happens to need, or mocking every dependency and inventing
a state for each.

Neither is the container the application runs. Neither can catch a missing registration, a
wrong lifetime, or a resolution that fails only once the full graph is present — which is
to say neither can catch the bugs DI configuration actually produces. The tests are
structurally blind to their own subject.

The mocking route has a second cost. Set-up code grows until it dwarfs the assertion, and
every mocked return value is a guess about how the real type behaves — a guess that stays
green after the real type changes.

> What passes is agreement between the test and its own fiction.

Here a test calls the same `AddRegistrations` the application calls, then `Replace`s what it
wants substituted. What runs under test is what runs in production, minus the parts
deliberately swapped. Mock the one thing the test is about — the clock, the payment gateway,
the thing that would hit the network — and let everything else be real. That is what makes
behavioural tests practical rather than only narrow unit tests around whatever was cheap to
fake.

There is a fifth, narrower one. A type exposed as a static `Instance` is normally outside DI
altogether: one instance per process, no way to substitute it, so everything depending on it
becomes untestable by association. `ServiceLocator` keeps such a type in the container and
lets a test point it at its own — a singleton stays a singleton in production without that
cost.

### When this is more than you need

Everything here solves a problem that appears at a certain size: composition spanning
several projects, tests that need the real dependency graph, a codebase where a silently
wrong registration costs more to find than it would have cost to prevent.

If the wiring fits on one screen and one person holds all of it in their head, this
machinery is overhead. `Program.cs` is simpler, and simpler is correct.

It stops being correct at the point where adding a service means opening a project you were
not working in — or the first time you ship a registration pointing at the wrong
implementation and spend an afternoon finding it.

## How the wiring fits together

Every project has a generated `DI/ServiceCollectionExtensions.g.cs` declaring one method:

```csharp
public static IServiceCollection AddRegistrations(this IServiceCollection services)
```

It does three things, in order: calls `AddRegistrations` on each project it directly
depends on, runs the registration scan over its own assembly, then calls
`AddManualRegistrations` — the hand-written seam.

Because each project cascades into its direct dependencies, the composition root only
calls the entry point. In a WPF application that is `App.xaml.cs`:

```csharp
protected override void OnStartup(StartupEventArgs e) {

    // The collection is a local: it exists only long enough to build the provider,
    // and ServiceLocator holds the result for the life of the process.
    var services = new ServiceCollection();
    XpEng.Coder03.Views.ServiceCollectionExtensions.AddRegistrations(services);
    XpEng.Coder80.Infrastructure.ServiceLocator.Initialize(services.BuildServiceProvider());

    // Nothing may resolve before Initialize has run — CurrentProvider throws until then.
    var mainView = XpEng.Coder80.Infrastructure.ServiceLocator.CurrentProvider.GetRequiredService<MainView>();
    mainView.Show();

    base.OnStartup(e);
}
```

Three things about that sequence are load-bearing:

- **`AddRegistrations` is called on the entry-point project only.** It cascades into
  everything else. Calling it on several projects is harmless but redundant.
- **`Initialize` comes after `BuildServiceProvider`,** and before anything resolves.
  `CurrentProvider` throws until it has run, naming its own cause.
- **The window is resolved, not constructed.** `new MainView()` would bypass the
  container and leave its dependencies unwired.

A console or service host differs only in what it resolves at the end; the three lines
before that are the same.

A project referenced by two others has `AddRegistrations` called twice. That is harmless:
the scan detects identical repeats and collapses them.

The shared components — the attribute, the interfaces, the scanner, the locator — are
generated once into **XpEng.Coder80.Infrastructure**, the deepest project, which every other project
already references transitively.

## Registering a type

Three mechanisms, chosen by who owns the type and whether reflection can construct it.

### `[Register]` — the default

You own the type and it has a **public** constructor.

```csharp
[Register]                                              // as itself, Singleton
[Register(typeof(IThing))]                              // against an interface
[Register(typeof(IThing), ServiceLifetime.Transient)]   // and a lifetime
public class Thing : IThing { }
```

`AllowMultiple`, so one class can be resolvable under several interfaces.

The public constructor matters: the scan activates types by reflection, which cannot reach
an `internal` or `protected` constructor. A type with one needs the next mechanism.

### `AddManualRegistrations` — you own it, reflection cannot build it

In `{Project}/ServiceCollectionExtensions.Manual.cs`. A factory written there is compiled
code in the same assembly, so it reaches a non-public constructor that reflection cannot.

```csharp
static partial void AddManualRegistrations(IServiceCollection services) {
    services.AddSingleton<MainViewModel>(_ => new MainViewModel());
    services.AddDbContext<AppDbContext>(o => o.UseSqlServer(connectionString));
}
```

Use it for a non-public constructor, an options lambda, or a lifetime decided at runtime.

This file is created once by DISetup and never regenerated.

### `IAddRegistrations` — you do not own the type

A scaffolded entity, generated code, something from a package — anything you cannot
decorate. Implement the interface in its own class under `DI/`:

```csharp
public class EntityLoaderRegistrations : IAddRegistrations {
    public void AddRegistrations(IServiceCollection services) {
        foreach (var type in Assembly.GetExecutingAssembly().GetTypes()) {
            // ...register whatever matches...
        }
    }
}
```

The scan finds every implementation, so any number can coexist — several code generators
can contribute to one project without colliding. Implementations need a public
parameterless constructor.

This is the mechanism most easily missed, and the answer whenever the type you want to
register is one you cannot edit.

## Replacing a registration

The three above all *add*. Replacing is a separate concern, and has its own interface.

```csharp
public class TestSubstitutions : IOverrideRegistrations {
    public void ReplaceRegistrations(IServiceCollection services) {
        services.AddTransient<IClock, FixedClock>();
    }
}
```

Overrides run last, after the scan and after every `IAddRegistrations` contributor, and
are exempt from duplicate validation — replacing is the declared intent. Use plain `Add*`
calls; the scanner removes whatever the same service type was registered as before.

Two uses: resolving a conflict between independently generated registrations, and
substituting behaviour in a test project.

### When registrations conflict

If two sources register the same service type differently, the scan throws and lists every
conflict at once:

```
Conflicting DI registrations in 'MyProject':
  MyProject.IThing -> MyProject.ThingA (Singleton), MyProject.ThingB (Singleton)
Use IOverrideRegistrations to replace a registration deliberately.
```

Identical repeats are not conflicts — those come from the same project being reached twice
through the dependency graph, and are collapsed silently.

## The service locator

A type should receive its **business domain** dependencies through its constructor —
the ones without which it would not be in a valid state.[^1] Those belong in the
signature, where the compiler enforces them and a reader can see what the type needs.

Two other kinds of dependency do not belong there.

**Those that cannot be injected.** A static `Instance` property has no constructor to
inject into. A view constructed by XAML is built by the framework, not the container. A
design-time fallback runs in a process where no container was ever built.[^2]

**Those that should not be injected.** Infrastructure a type merely *uses* rather than
*is defined by* — a logger, a connection, a performance counter — is not part of what
makes an instance valid. Threading it through every constructor adds a parameter to
every type and a line to every call site, obscuring the dependencies that do matter.
Lazily instantiated properties are the same case: the point is to defer the cost until
something asks, which a constructor parameter defeats.[^3]

For both, resolve at the point of use:

```csharp
// Infrastructure — used, not definitional. Resolved per access, not stored.
private ILogger Logger => XpEng.Coder80.Infrastructure.ServiceLocator.CurrentProvider.GetRequiredService<ILogger>();

// Lazy property — the cost is paid on first read, not on construction.
private IReportBuilder Builder => field ??= XpEng.Coder80.Infrastructure.ServiceLocator.CurrentProvider.GetRequiredService<IReportBuilder>();

// Static Instance — no constructor to inject into.
public static MainModel Instance => DesignTimeSingleton<MainModel>.Resolve(() => new MainModel());
```

`Initialize` is called once at startup. `CurrentProvider` throws rather than returning
null when nothing has been initialized, so the failure names its own cause.

The line to hold: if a dependency defines what the type *is*, it goes in the
constructor. If it is something the type *uses*, the locator is the better place.

[^1]: A repository an order service cannot function without; a validator a form is
    meaningless without. Constructing one of these without its dependency should be
    impossible, which is exactly what a constructor parameter guarantees.

[^2]: See `DesignTimeSingleton`, which resolves from the container and falls back to a
    directly constructed instance only when the process is the XAML designer's — so a
    resolution failure in production or in a test still propagates as a real bug.

[^3]: `field ??=` in a property getter resolves once, on first access, and caches. A
    constructor parameter would resolve for every instance whether or not anything
    ever reads it.

## Testing

### The problem

A `ServiceCollection` is an ordinary object, so building one per test gives complete
isolation for free. But code reached *through the locator* — anything calling
`SomeType.Instance` — does not resolve from your provider. It resolves from whatever
`ServiceLocator` currently holds, which without care means whatever the last test set.

### Most tests need nothing special

If the code under test receives its dependencies through its constructor, resolve directly
and ignore the locator entirely:

```csharp
var services = new ServiceCollection();
XpEng.Coder03.Views.ServiceCollectionExtensions.AddRegistrations(services);
var provider = services.BuildServiceProvider();

var thing = provider.GetRequiredService<IThing>();
```

No scoping, no cleanup beyond disposing the provider. Prefer this.

### When the code calls `.Instance`

Then the locator has to point at your container for the duration of the test:

```csharp
using (ServiceLocator.UseProvider(provider)) {
    var model = MainModel.Instance;   // resolves from YOUR provider
}
```

Disposing restores whatever was in effect before, so nested and sequential scopes both
behave. The scope uses `AsyncLocal` rather than `[ThreadStatic]`: a thread-static value
does not survive an `await` — the continuation can resume on a different pool thread — so
an async test would silently fall back to the default provider.

### Substituting a registration

```csharp
var services = new ServiceCollection();
XpEng.Coder03.Views.ServiceCollectionExtensions.AddRegistrations(services);
services.Replace(ServiceDescriptor.Transient<IClock, FixedClock>());
```

`Replace` after `AddRegistrations`, not before: it matches on service type regardless of
how the original was registered, so it supersedes even a factory registration. One
statement rather than a remove followed by an add, so there is no stale descriptor to
leave behind if the removal misses.

`Microsoft.Extensions.DependencyInjection.Extensions` provides `Replace` and `RemoveAll`.

### Composing the pieces

A base class layers suite-wide substitutions under per-test ones:

```csharp
public abstract class TestBase {

    protected ServiceProvider Provider { get; private set; } = null!;
    private IDisposable? _scope;

    [TestInitialize] public void Initialize() => BuildProvider(null);
    [TestCleanup]    public void Teardown()   => ReleaseProvider();

    /// Suite-wide registrations. Derived classes call base first, then layer their own.
    protected virtual void ConfigureServices(IServiceCollection services) {
        XpEng.Coder03.Views.ServiceCollectionExtensions.AddRegistrations(services);
    }

    protected void RebuildProviderWithOverrides(Action<IServiceCollection> overrides) {
        ReleaseProvider();
        BuildProvider(overrides);
    }

    private void BuildProvider(Action<IServiceCollection>? overrides) {
        var services = new ServiceCollection();
        ConfigureServices(services);
        overrides?.Invoke(services);

        Provider = services.BuildServiceProvider();
        _scope = ServiceLocator.UseProvider(Provider);
    }

    private void ReleaseProvider() {
        // Provider FIRST. Disposing it disposes the services it created, and their Dispose
        // methods may resolve through the locator — releasing the scope first would leave
        // them with no provider to reach.
        Provider?.Dispose();
        _scope?.Dispose();
        _scope = null;
    }
}
```

That disposal order is not obvious until it bites: a service whose `Dispose` touches
`.Instance` throws during teardown if the scope has already gone.

One related trap: a lazy property read from inside `Dispose` **constructs** the object it
is trying to dispose. Read the backing field there, not the property.
